# Техническое задание: «Клинический компас» — цифровой ассистент врача

Версия 0.1 · 20.10.2026

## 1. Общие сведения

| Пункт | Значение |
|---|---|
| Проект | «Клинический компас»: веб-приложение (PWA) для сопровождения терапии тревожных и депрессивных расстройств |
| Контекст | Кейс-чемпионат «Цифровой ассистент врача» |
| Организаторы кейса | «Авинейро» (ГК «ХимРар»), НМИЦ ПН им. В. П. Сербского, Сеченовский Университет |
| Онлайн-предзащита | 28.10.2026 |
| Финал и демодень | 30.10.2026 |
| Репозиторий | `git@github.com:Ellkon/psychometr.git` |

## 2. Цель и граница ответственности

**Цель.** Сократить время подготовки клинической сводки, помочь проверить безопасность терапии и показать врачу объяснимые основания для направления к психиатру.

**Первый пользователь:** врач первичного звена (терапевт, невролог) и психиатр. Пациент заполняет шкалы и дневник между визитами.

**Граница ответственности.** Ассистент собирает и структурирует сведения, считает баллы шкал, показывает предупреждения и источники. Диагноз и лечение определяет врач. Система не формирует назначений автоматически и не выдаёт off-label-рекомендаций.

## 3. Роли

| Роль | Возможности |
|---|---|
| `patient` | Заполняет назначенные шкалы, дневник доз и нежелательных явлений (НЯ), короткие check-in. Видит свои результаты и пояснение к каждой шкале. Видит статус доставки своих сигналов. |
| `doctor` | Ведёт только своих пациентов (care team). Создаёт пациента и приглашение. Видит реестр, таймлайн, карточки подсказок, алерты. Подтверждает или отклоняет подсказки и алерты. Отзывает сессии пациента. |
| `admin` | Управляет учётными записями врачей и привязками. Просматривает журнал аудита. Клинические данные пациентов не видит, кроме случаев, где это явно разрешено. |

## 4. Функциональные требования

### FR-1. Вход пациента по приглашению
- FR-1.1. Врач создаёт пациента и нажимает «Пригласить». Система генерирует одноразовую ссылку `https://<host>/i/<token>` (32 байта, CSPRNG, base64url) и 6-значный код (CSPRNG).
- FR-1.2. В БД хранятся только хэши: токен в SHA-256, код в argon2id. Также хранятся `patient_id`, `created_by`, `expires_at` (72 ч), `used_at`, `attempts`, `status`.
- FR-1.3. Код показывается врачу один раз. Интерфейс подсказывает передать ссылку и код по разным каналам.
- FR-1.4. Пациент открывает ссылку и вводит код. После 5 неверных попыток приглашение блокируется. Действует rate-limit по IP и по токену.
- FR-1.5. После успешного входа устройство привязывается (refresh-сессия на 30 дней). Повторный вход на этом устройстве выполняется по личному коду пациента. Для нового устройства нужно новое приглашение.
- FR-1.6. Врач видит статус приглашения (отправлено / использовано / истекло / заблокировано), может перевыпустить его и отозвать все сессии пациента.
- FR-1.7. Токен удаляется из адресной строки сразу после загрузки страницы и не попадает в логи и Referer.

### FR-2. Вход врача и администратора
- Вход по email и паролю (argon2id). Access JWT живёт 15 минут, refresh-cookie `httpOnly; Secure; SameSite=Strict` с ротацией и отзывом.
- Блокировка после серии неудачных попыток, rate-limit.
- Автовыход при неактивности.
- TOTP 2FA (желательно к 28.10; иначе в дорожную карту).

### FR-3. Шкалы и самоотчёт
- FR-3.1. PHQ-9 и GAD-7 описываются JSON-формами в `content/scales/`. Тексты пунктов дословно совпадают с валидированной русскоязычной версией.
- FR-3.2. Каждая форма содержит паспорт: `id`, `title`, `version`, `validation_citation_ru`, `license_status`, `cutoffs`, `recall_period`, `reviewed_at`.
- FR-3.3. Балл считается на сервере. Ответ сохраняется вместе с версией формы.
- FR-3.4. Расписание шкал задаёт врач. Окно заполнения гибкое. Пропуски видны врачу как сигнал.
- FR-3.5. Ежедневное самочувствие собирается отдельным коротким дневником; период оценки PHQ-9/GAD-7 не меняется.
- FR-3.6. Шкалы с неподтверждённой лицензией (HADS, BDI-II, MMAS) не подключаются.

### FR-4. Движок правил и карточки подсказок
- FR-4.1. Правила — данные: JSON decision tables (GoRules ZEN) в `content/rules/`.
- FR-4.2. У каждого правила есть `id`, `version`, `source` (КР ID + номер тезиса / ГРЛС + дата инструкции), `severity` (`info` | `warning` | `critical`), `message`, `suggested_action`.
- FR-4.3. Ответ движка — карточка в стиле CDS Hooks: текст, уровень, источник, версия правила, входные факты, предлагаемое действие.
- FR-4.4. Любое предлагаемое действие требует подтверждения врачом (Task: `requested → accepted | rejected`, с комментарием).
- FR-4.5. Каждое срабатывание записывается в журнал с таймстемпом и версией правила.
- FR-4.6. Справочник препарата («Авиандр» и альтернативы из КР) хранится JSON-файлом в `content/drugs/`: показания (МКБ-10), противопоказания как проверяемые условия, взаимодействия с классом тяжести, режим дозирования, НЯ. Содержимое — кандидаты для сверки с ГРЛС, а не готовый протокол.
- FR-4.7. Отсутствующие сведения (беременность, функция почек и печени, сопутствующие препараты) хранятся как `unknown`, а не `false`, и формируют список уточнений.

### FR-5. Маршрутизация к психиатру
- FR-5.1. Категории «обязательно» и «желательно» плюс отдельный уровень срочности.
- FR-5.2. Критерии берутся из `content/rules/routing.*` и объясняются одной фразой со ссылкой на источник. Пороги — проект для клинического согласования.
- FR-5.3. Ответ > 0 на пункт 9 PHQ-9 — триггер дополнительной оценки риска (critical-алерт врачу). Это не автоматическое заключение о непосредственной угрозе.
- FR-5.4. При самоотчёте с признаками непосредственной опасности пациенту сразу показывается инструкция по экстренной помощи (доступна офлайн). Пациенту не предлагается ждать ответа врача.

### FR-6. Дневник доз и нежелательных явлений
- Отметка приёма дозы в 1–2 действия, напоминания, запись НЯ.
- Метрика: доля отмеченных доз от назначенных за период (самоотчёт; не называть PDC/MPR).
- Кандидат уведомления: пропуск двух доз подряд. Порог настраивается правилом.

### FR-7. Экран врача
- FR-7.1. Реестр пациентов (по модели Collaborative Care): последний балл, изменение, недель без контакта, флаги, статус «не заполнено» / «просмотрено врачом».
- FR-7.2. Таймлайн пациента: баллы шкал, назначенная терапия, отмеченные дозы, НЯ, контакты, алерты.
- FR-7.3. Целевой сценарий «открыть пациента и понять ситуацию» укладывается в 3–4 клика и меньше 60 секунд. Это гипотеза, её нужно измерить.

### FR-8. Алертинг
- FR-8.1. Transactional outbox в PostgreSQL и доставка по WebSocket.
- FR-8.2. Состояния `pending → sent → delivered → acknowledged` с таймстемпом каждого перехода и `idempotency_key`.
- FR-8.3. Неподтверждённый critical-алерт эскалируется по таймеру резервному получателю: через 30 минут следующему врачу care team. Алерты снятого врача переадресуются сразу. Единственного врача пациента снять нельзя, сначала назначается другой.
- FR-8.4. Уровни тяжести визуально различимы. Жёстких сигналов мало, остальное отображается неинтрузивно (защита от alert fatigue).

### FR-9. Офлайн
- Клиентская очередь в IndexedDB (Dexie) с `idempotency_key`. После восстановления связи данные досылаются без дублей.
- Пациент видит, что отправка не доставлена.
- В очереди хранится минимум данных; при выходе из аккаунта она очищается.

### FR-10. Аудит
- Записываются: вход и выход, просмотр карты, изменения, подтверждения и отклонения, отказы в доступе, операции с приглашениями.
- Журнал append-only, с хэш-цепочкой.
- Администратор просматривает журнал на отдельном экране.

### FR-11. Согласие
- При первом входе пациент даёт согласие на обработку ПДн. Сохраняются версия текста, время и IP.

## 5. Нефункциональные требования

### NFR-1. Безопасность
Данные о здоровье относятся к специальной категории ПДн (152-ФЗ) и составляют врачебную тайну (323-ФЗ).

| № | Требование |
|---|---|
| S-1 | Только HTTPS/WSS (Caddy, HSTS). PostgreSQL доступен только во внутренней docker-сети. |
| S-2 | RBAC и объектная проверка через единую функцию `assertCanAccessPatient()` во всех роутах с данными пациента. |
| S-3 | Идентификаторы личности (ФИО, телефон, дата рождения, СНИЛС) хранятся в таблице `patient_identity` и шифруются в приложении (AES-256-GCM; ключ в секрете, не в БД). Клинические таблицы ссылаются только на UUID. |
| S-4 | Роли БД: `app` (DML без DDL; для `audit_event` только INSERT/SELECT) и `migrator`. |
| S-5 | `@fastify/helmet`: строгий CSP без inline-скриптов, `frame-ancestors 'none'`, `Referrer-Policy: no-referrer`. |
| S-6 | Никаких сторонних трекеров, аналитики, CDN и внешних шрифтов. Все ресурсы self-hosted. |
| S-7 | Все входные данные валидируются zod. SQL только через Drizzle (параметризованные запросы). |
| S-8 | Логи pino с redact: ПДн, клинические данные, токены и коды в лог не попадают. |
| S-9 | Секреты хранятся только в `.env` / docker secrets и не коммитятся. В CI работает gitleaks. |
| S-10 | Бэкапы: `pg_dump`, шифрование `age`, хранение в РФ. Восстановление проверено. |
| S-11 | Уведомления вне приложения (SMS, push) не содержат медицинского текста. |

### NFR-2. Аудиты безопасности
- **Каждый PR (CI):** Semgrep (`p/typescript`, `p/owasp-top-ten`, `p/jwt`), eslint-plugin-security, gitleaks, `pnpm audit --audit-level=high`, Trivy (fail на HIGH/CRITICAL), OWASP ZAP baseline против стека в docker compose, IDOR-матрица «роль × эндпоинт × чужой пациент».
- **Перед merge фичи:** security review диффа (инструментом агента или вручную по `AGENTS.md`).
- **Ручные аудиты:** 27.10 и 29.10. Чеклист OWASP ASVS L2 (V2, V3, V4, V7, V8, V9) и OWASP Top 10, ZAP full scan, ручная попытка обхода приглашения и IDOR. Отчёт сохраняется в `docs/security/audit-YYYY-MM-DD.md`.
- **Модель угроз:** `SECURITY.md` (облегчённая STRIDE).
- **Рантайм:** алерт администратору при аномалиях: 20 и более отказов в доступе или 10 и более неверных паролей и кодов за 5 минут. Сигнал содержит только счётчик.

### NFR-3. Производительность
- Нагрузочный тест k6 с заданным числом одновременных пользователей. Отчёт содержит p95 времени ответа и долю ошибок.
- Метрики Prometheus (`fastify-metrics`), в том числе время доставки алерта. `/metrics` не проксируется наружу и требует bearer-токен.
- Лимит запросов считается по проверенному пользователю (клиника за NAT не ограничивается как один клиент), без токена — по IP.

### NFR-4. Надёжность
- Сценарии сбоя проверяются по отдельности: обрыв на клиенте, падение сервера, повторная отправка, восстановление из бэкапа. RPO и RTO измеряются, а не декларируются.

### NFR-5. Локализация и хостинг
- Интерфейс на русском языке.
- Хостинг в РФ (Yandex Cloud / Selectel / VK Cloud), шифрованные диски.

### NFR-6. Расширяемость
- Новая шкала, препарат или правило добавляется JSON-файлом в `content/` без изменения кода ядра, с сохранением версии.

## 6. Архитектура и стек

```
apps/web  (React PWA) ──HTTPS/WSS──> Caddy ──> apps/api (Fastify) ──> PostgreSQL
                                                   │
                                                   ├─ ZEN Engine (content/rules)
                                                   └─ outbox worker (алерты, эскалация)
```

| Слой | Технологии |
|---|---|
| Monorepo | pnpm workspaces: `apps/api`, `apps/web`, `packages/shared`, `content/` |
| Backend | Node 22, Fastify, TypeScript strict, `@fastify/websocket`, `fastify-type-provider-zod`, `@fastify/helmet`, `@fastify/rate-limit`, pino |
| БД | PostgreSQL 16, Drizzle ORM, drizzle-kit |
| Правила | `@gorules/zen-engine` |
| Frontend | React 19, Vite, vite-plugin-pwa, TanStack Router, TanStack Query, shadcn/ui, Tailwind, Recharts, Dexie |
| Общие схемы | zod в `packages/shared` (используются и фронтом, и бэком) |
| Тесты | Vitest, Playwright, k6 |
| Инфраструктура | Docker Compose (postgres, api, web/Caddy), GitHub Actions |

LLM в текущем объёме не используется.

## 7. Модель данных (черновик)

## 8. Контент как данные

```
content/
  scales/phq9.ru.json      # паспорт + пункты + scoring + cutoffs
  scales/gad7.ru.json
  drugs/aviandr.json       # кандидаты правил для сверки с ГРЛС
  rules/safety.json        # противопоказания, взаимодействия
  rules/routing.json       # маршрутизация обязательно/желательно
  rules/adherence.json
  sources.json             # реестр источников (КР, ГРЛС, публикации валидации)
```

- Каждое правило ссылается на запись в `sources.json`.
- Для каждого файла правил есть эталонные тест-сценарии (`content/**/__cases__/*.json`), которые прогоняются в CI.

## 9. Вне объёма

- LLM-извлечение анамнеза и любая генерация текста.
- Собственный диагностический ИИ, автономная терапия.
- Датчики приёма, голосовая диагностика, пассивные сенсоры.
- Развёртывание mindLAMP / RADAR-base.
- Видеоконсультации.
- Telegram и другие внешние каналы с медицинскими данными.
- Коммерческие API (РЛС, Vidal, Galenos) — только в дорожной карте.

## 10. Приёмка (демонстрация жюри)

| Метрика | Сценарий | Артефакт |
|---|---|---|
| Объяснимость | Открыть подсказку | Источник КР/ГРЛС, версия правила, входные факты |
| Неполные данные | Пациент без сведений о функции почек | Список уточнений вместо ошибки |
| Эргономика | Типовой сценарий врача | Измеренные клики и время (Playwright) |
| Алертинг | PHQ-9 п.9 > 0: доставка, подтверждение, эскалация | Таймстемпы, p95, журнал |
| Нагрузка | k6 | p95, доля ошибок |
| Сбой | Обрыв связи при отправке, падение сервера, восстановление из бэкапа | Отсутствие дублей, измеренные RPO/RTO |
| Гибкость | Добавить шкалу или правило файлом | Работа без изменения кода, версия сохранена |
| Безопасность | Доступ к чужому пациенту, обход приглашения, просмотр аудита | 403 + запись аудита, матрица прав, схема контура, отчёт аудита |

Апробация включает синтетические сценарии и экспертную проверку врачами. Она не заменяет клинических испытаний.

## 12. Открытые вопросы

- Алерт по нежелательному явлению: нужен клинический источник и правило в `content/rules`. Пока НЯ видны врачу в реестре и таймлайне без алерта.
- Ежедневный дневник самочувствия (FR-3.5): нужен согласованный текст вопросов.

- Клиническое согласование порогов маршрутизации и протокола кризисной эскалации.
- Сверка данных «Авиандра» с актуальной инструкцией в ГРЛС.
- Подтверждение условий использования русских версий PHQ-9 и GAD-7 и ссылок на работы по валидации.
- Выбор клиники и первого пользователя для пилота.
