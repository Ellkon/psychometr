# Этап 2 — доступ, identity и аудит

22.10.2026. Требования: FR-1, FR-2 (без TOTP), FR-10, FR-11;
NFR-1 S-1…S-9 в части этого этапа, NFR-2 (IDOR и проверки безопасности).

## Как устроено

- **11 таблиц:** `users`, `practitioners`, `patients`, `patient_identity`, `care_team`,
  `patient_invites`, `patient_devices`, `sessions`, `refresh_tokens`, `consents`,
  `audit_events`. Таблицы шкал, терапии и алертов добавляются со своими функциями
  на следующих этапах, а не заполняются вымышленными клиническими полями сейчас.
- Схема создана `drizzle-kit generate`; отдельная custom-миграция задаёт права и
  immutable-триггеры. Применённые миграции не редактировать.
- `migrator` выполняет DDL отдельным одноразовым сервисом. API работает только
  под `app`; ему нельзя создавать таблицы. `audit_events` и `consents` доступны
  только на INSERT/SELECT, UPDATE/DELETE/TRUNCATE запрещены также триггерами.
- `patient_identity` содержит только AES-256-GCM ciphertext, случайный 12-байтный
  nonce, 16-байтный tag и версию ключа. UUID пациента связан с шифротекстом через
  AAD: перестановка записей между пациентами не расшифруется. IP согласия тоже
  шифруется, с отдельным назначением AAD. UUID нормализуются до проверки
  доступа и формирования AAD/аудита, как в PostgreSQL. Ключ 32 байта в `.env`, не в БД.
- Пароли и личные коды: Argon2id/v19, 19 MiB, 2 прохода, 1 поток, случайная соль.
  Приглашение: 32 случайных байта в base64url + 6 цифр `crypto.randomInt`,
  срок 72 часа, блокировка после пяти ошибок. Только SHA-256 токена и Argon2id
  кода в БД. Проверка и погашение атомарны, включая параллельные запросы.
- Перевыпуск отменяет прежнее неиспользованное приглашение. Ссылка/код видны
  врачу один раз. Второе устройство требует нового приглашения **и уже
  установленного личного кода**: приглашение не служит скрытым сбросом PIN.
- Access JWT (jose, только HS256, проверяются issuer/audience/exp/iat/sid/sub)
  живёт 15 минут и хранится только в памяти страницы. Сессия проверяется в БД
  при каждом запросе: отзыв действует до истечения JWT.
- Refresh — **не JWT**, а случайный непрозрачный токен. Cookie
  `__Host-compass-refresh`: HttpOnly, Secure, SameSite=Strict, Path=/, без Domain.
  В БД только хэши. При обновлении старый токен помечается использованным;
  его повторное предъявление отзывает семейство сессии. История хэшей нужна
  для обнаружения повторов, а не хранит открытые токены.
- Абсолютный срок сессии — 30 дней, тайм-аут неактивности — 15 минут. Refresh
  сам по себе не продлевает неактивность. UI отправляет редкий запрос `/auth/me`
  только при реальном действии пользователя, а не фоновым таймером.
- `__Host-compass-device` — отдельная привязка устройства. После logout она
  остаётся, но **сама не даёт входа**: нужен личный код. Отзыв врачом удаляет
  возможность входа и по старой привязке, и по refresh, и по access-токену.
- Все мутации требуют точного `Origin == PUBLIC_ORIGIN`; cookie защищены
  SameSite. Auth ограничен по IP, приглашения дополнительно — по хэшу токена.
- Код `/i/<token>` убирается синхронным локальным скриптом до React/router.
  Секрет не попадает в history.state, localStorage, Referer и серверные логи.
  API/приглашения имеют `Cache-Control: no-store`; PWA не кеширует API.

## Права

| Действие | Врач | Пациент | Администратор |
| --- | --- | --- | --- |
| Создать пациента | Да, становится членом care team | Нет | Нет |
| Прочитать identity | Только свой care team | Только себя | Нет |
| Изменить identity / приглашения / отзыв сессий | Только свой care team | Нет | Нет |
| Назначить врача по UUID | Нет | Нет | Да, без чтения identity |
| Создать врача / читать аудит | Нет | Нет | Да |

Везде с пациентом используется `assertCanAccessPatient()`. Режим `assignment`
даёт администратору только административную операцию, не клиническое чтение.
Режим `create` применяется к UUID, созданному сервером, до записи новых данных.
Активация приглашения создаёт principal только после проверки секретного
одноразового приглашения; произвольный patientId в теле не принимается.

Аудит содержит UUID, тип действия, время и хэш-цепочку — без ФИО, токенов,
паролей, кодов, IP и клинических ответов. Дописывание цепочки сериализуется
advisory-lock транзакции; ожидаемые отказы коммитят запись отказа, неожиданные
ошибки откатывают операцию. Строки ошибок SQL/валидации не логируются.

## Клиент

TanStack Router/Query, адаптированные shadcn/ui Input/Card (MIT, лицензия рядом
с компонентами), Tailwind. Только локальные ассеты. Query-кеш — в памяти;
при смене пользователя он очищается, старые ответы после logout отбрасываются.
Web Locks сериализуют cookie-операции между вкладками, внутри вкладки refresh
объединяется в один запрос. Logout уведомляет другие вкладки.

IndexedDB пока не используется приложением для хранения данных. При logout
удаляется зарезервированная будущая очередь `compass-outbox`; это проверено
браузерным тестом. Единственная запись localStorage — булев флаг незавершённого
**офлайн-выхода**, без пользователя, JWT или медицинских данных. Пока флаг есть,
автовосстановление сессии заблокировано до успешного серверного logout.

В этапе 1 lock-файл был создан до включения защиты цепочки поставок. При
добавлении новых пакетов обнаружились слишком свежие ранее зафиксированные
версии и старые зависимости без provenance. Проверки **не отключались**:
выбраны зрелые версии eslint/Turbo/typescript-eslint/Vitest/TanStack/Vite.
Overrides для Vite 8.3.4 и browserslist 4.29.3 выравнивают автоматические peer
зависимости под семидневное окно; `@trickfilm400/rollup-plugin-off-main-thread`
обновлён до 4.0.0 (Apache-2.0, с provenance), legacy semver 6.3.1 заменён на
7.7.3 (ISC, с provenance). Полная PWA-сборка после этого проверена.

Нативный PostgreSQL разрешён в `pnpm.onlyBuiltDependencies` только для его
явно перечисленных платформ: postinstall восстанавливает symlink'и библиотек.
В production-образ эти dev-зависимости не попадают. Из-за стороннего exit-hook
API-тесты дополнительно требуют успешный JSON-отчёт: ошибка/пропуск тестов не
может замаскироваться нулевым кодом завершения процесса.

## Проверка без Docker

`pnpm test` запускает PostgreSQL через приватный Unix-сокет, миграции выполняет
ролью migrator, приложение тестирует под ролью app. Все данные синтетические,
каталог БД удаляется при завершении. Тесты не обращаются во внешнюю сеть.

Для локального браузерного прогона после `pnpm build` можно использовать
`LOCAL_E2E=1`: Playwright сам поднимет тестовый HTTPS-адаптер и PostgreSQL.
Нужны `openssl`, установленные браузеры Playwright, и переданные в окружение
синтетические `ADMIN_EMAIL`/`ADMIN_PASSWORD`. При необходимости разрешён путь
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` к локальному Chromium. Никакие флаги
отключения web security/CSP не используются.

Тестовый HTTPS-адаптер **не является production-сервером** и исключён из
сборки API. CI использует именно Compose + Caddy, а не этот адаптер.

## Что намеренно ещё не готово

- Утверждённый юридический текст согласия; без него активация закрыта.
- TOTP 2FA (дорожная карта к предзащите), безопасное восстановление пароля/PIN,
  смена первоначального пароля, полный жизненный цикл учётных записей.
- Ротация ключа identity с перешифрованием, очистка истёкших служебных записей,
  внешнее закрепление последнего audit-хэша, алерты при аномалиях.
- Клинические таблицы и формы, реестр с баллами, rules engine, outbox/offline
  отправка, мониторинг, проверенный restore бэкапа — последующие этапы.
- Полный ASVS-аудит, юридическое и инфраструктурное согласование размещения
  медицинских данных в РФ. Автотесты не доказывают соответствие 152-ФЗ/323-ФЗ.
