# Этапы 7–8 — аудит, мониторинг, нагрузка, сбои, бэкап

25.10.2026. Требования: NFR-2 (аудит, рантайм-сигналы), NFR-3 (k6, Prometheus), NFR-4 (сценарии
сбоя, измеренные RPO и RTO), S-10 (бэкап `pg_dump` + `age`, проверенное восстановление).
Стенд: docker compose (PostgreSQL 16, API, Caddy) на WSL2, только синтетические данные.

## Аудит безопасности

Отчёт: [`docs/security/audit-2026-10-25.md`](../security/audit-2026-10-25.md). Найдено и закрыто
четыре высоких находки (повторные critical-алерты от GAD-7, голодание диспетчера, снятие
единственного врача, усечённый бэкап с отметкой об успехе) и ряд средних и низких. Открытые
пункты перечислены в отчёте.

## Рантайм-сигналы администратору (NFR-2)

`apps/api/src/domain/security-signals.ts`, таблица `security_signals` (миграции 0009–0010).
Воркер раз в 30 секунд считает в журнале аудита события за последние 5 минут:

- `access_denied_spike` — отказы в доступе к объектам (`access.denied`), порог 20;
- `auth_failure_spike` — неверные пароли и коды приглашений, блокировки, порог 10.

Один сигнал на вид и пятиминутное окно. Сигнал содержит только счётчик, без ПДн. Администратор
видит его над страницей и подтверждает; подробности — в журнале аудита. Пороги — в
`packages/shared/src/security.ts`.

## Метрики (NFR-3)

`fastify-metrics` (MIT): время ответа по шаблонам маршрутов (без идентификаторов пациентов),
метрики процесса, `compass_alert_delivery_seconds` (создание → подтверждение получения
клиентом врача) и `compass_alert_acknowledgement_seconds` (создание → подтверждение врачом).
`/metrics` вне `/api`, поэтому Caddy его не отдаёт; внутри сети Docker нужен bearer-токен
`METRICS_TOKEN`. Без токена эндпоинт не создаётся.

## Нагрузка (NFR-3)

Сценарий: [`infra/load/k6-clinical-compass.js`](../../infra/load/k6-clinical-compass.js). Setup
создаёт врачей и пациентов через настоящие приглашения. Дальше параллельно работают:

- врачи: реестр, терапия, карточки, таймлайн, алерты;
- пациенты: список шкал, PHQ-9 с повтором той же отправки (каждый десятый с п. 9 > 0, то есть
  с критическим алертом), повторная отметка дозы, просмотр терапии. Пауза между действиями — 2 с.

| Прогон                                               | Запросов | p95 общий | p95 врачи | p95 пациенты | Ошибки        |
| ---------------------------------------------------- | -------- | --------- | --------- | ------------ | ------------- |
| 20 пользователей, 2 мин (до исправления реестра)     | 5498     | 135 мс    | 204 мс    | 106 мс       | 12 × 500      |
| 20 пользователей, 2 мин, 2 сеанса на одного врача    | 5538     | 134 мс    | 190 мс    | 101 мс       | 0 × 5xx, 4 % 429 |
| 20 пользователей, 2 мин, один сеанс на учётную запись | 5642     | 97 мс     | 114 мс    | 87 мс        | 0             |

Первый прогон нашёл ошибку: реестр отдавал 500, если отметка дозы появлялась во время чтения
(отрицательное число недель без контакта). Исправлено, есть регресс-тест. Во втором прогоне
два сеанса одного врача без пауз упёрлись в лимит 300 запросов в минуту на пользователя — это
ожидаемое поведение лимита. Повтор отправки PHQ-9 во всех прогонах возвращал тот же ответ,
дублей не было.

Лимит запросов считается по проверенному пользователю: клиника за одним NAT-адресом не
ограничивается как один клиент. Без токена или с поддельным токеном счёт идёт по IP.

## Сценарии сбоя (NFR-4)

| Сценарий                          | Что сделано                                     | Результат                                                                                     |
| --------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Обрыв на клиенте                  | Playwright: отметка дозы без сети               | Отметка в очереди, «Не отправлено: 1»; после восстановления связи сохранена один раз          |
| Повторная отправка                | k6 и интеграционные тесты                       | Повтор PHQ-9 и отметки дозы — тот же результат; 10 параллельных повторов — один алерт         |
| Перезапуск PostgreSQL             | `docker compose restart db` при работающем API  | API не упал (обработчик ошибок пула), `/api/ready` снова 200 через 2 с                       |
| Падение API                       | `docker compose kill -s SIGKILL api`, `up -d`   | API снова отвечает через 7,8 с. Транзакции не оставляют частичных записей; неотправленные алерты хранятся в `alerts` и уходят при подключении врача |
| Восстановление из бэкапа          | `restore-verify`                                | RTO 1,75 с, число строк в 13 таблицах совпадает с рабочей БД                                  |

RPO равен интервалу бэкапов (для стенда — час, см. [`infra/backup/README.md`](../../infra/backup/README.md)).

## Бэкап (S-10)

Подробно — [`infra/backup/README.md`](../../infra/backup/README.md). Открытый дамп на диск не
пишется, файлы 0600, расшифровка чужим ключом отклоняется, упавший `pg_dump` даёт ошибку без
файла. Не сделано: выгрузка копий в хранилище в РФ вне сервера (нужно хранилище заказчика) и
отдельная роль с `pg_read_all_data` вместо суперпользователя.
