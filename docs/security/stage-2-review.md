# Проверка этапа 2 — 22.10.2026

Это проверка реализации этапа, **не** полный аудит ASVS и не заключение
о готовности работать с настоящими медицинскими данными.

## Выполнено локально

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, сборка, формат и валидация контента.
- 80 тестов: 60 API, 6 shared, 7 web, 7 инфраструктурных/раннего удаления токена.
- В API-тестах — настоящая PostgreSQL 16, новые миграции и реальная роль `app`.
  Проверены запрет DDL, UPDATE/DELETE/TRUNCATE аудита и изменения согласий.
- Матрица пяти пациентских роутов × пяти вариантов роли/принадлежности,
  а также управление care team, создание учётных записей и чтение аудита.
- Параллельные попытки погашения приглашения и перебора кода; refresh replay;
  немедленный отзыв доступа; согласие и отсутствие consent-конфигурации;
  TTL, неактивность, Origin/CSRF, Argon2id, подмена AES-GCM и цепочка аудита.
- Реальный Chromium через Playwright: 3 сценария, включая полный путь
  врач → приглашение → согласие → пациент → logout → PIN → отзыв врачом.
  Проверены Secure/HttpOnly/SameSite cookies, отсутствие токена в URL/Referer,
  очистка IndexedDB и `Cache-Control: no-store` для данных.
- Локальный Semgrep по доступным из GitHub наборам JS/TS/Dockerfile/GitHub
  Actions/pnpm: находок нет. Это дополнительный прогон, не замена точным
  registry-пакетам `p/typescript`, `p/owasp-top-ten`, `p/jwt` в CI.
- `pnpm audit --audit-level=high`: HIGH/CRITICAL отсутствуют; есть одна MODERATE
  в dev-инструменте (esbuild через drizzle-kit), не в рабочем API-образе.

## Проверка 12 правил AGENTS.md

1. Пациентские операции проходят единую проверку доступа; IDOR тестируется.
2. Identity шифруется и хранится отдельно; UUID используется в связях.
3. Логи не содержат сырой URL, тела запроса, SQL-параметров и текста ошибок;
   redact расширен, есть тест на маркеры-секреты и ПДн.
4. Нет внешних клиентских ресурсов, аналитики и шрифтов.
5. `.env` генерируется локально, игнорируется Git/Docker, секреты не печатаются;
   новые переменные перечислены с пустыми значениями в `.env.example`.
6. Вход/выход, приглашения, отказы, карты и изменения имеют аудит; цепочка
   сериализована, неизменяемость ограничена и правами, и триггерами.
7. Токен и код — только `crypto.randomBytes` / `randomInt`, в БД только хэши.
8. Пароли/PIN — Argon2id, identity — стандартный AES-256-GCM Node.
9. Контракты входа/выхода находятся в shared, внешний ввод проверяется zod.
10. Helmet и строгий CSP сохранены, `unsafe-inline` / `unsafe-eval` не добавлены.
11. Уведомлений вне приложения пока нет; UI предупреждает не добавлять
    медицинские сведения при передаче приглашения.
12. Медицинских данных/JWT в localStorage нет; очередь удаляется при logout.
    Один boolean-маркер офлайн-выхода не содержит данных пациента.

## Границы локальной проверки и приёмка CI

- До публикации этапа 2 новые Dockerfile/Compose/Caddy проверялись только
  по конфигурации. Теперь оба этапа входят в общий [PR #2](https://github.com/Sirsolar12/psychometr/pull/2).
  Результаты именно его последнего коммита во вкладке Checks — источник статуса CI;
  прежний зелёный прогон этапа 1 сам по себе не подтверждает этап 2.
- Локальный браузерный прогон использовал тестовый HTTPS-адаптер, а не Caddy.
  Сборка образов, ZAP baseline, Trivy и браузерный сценарий через Caddy включены в CI.
- Gitleaks и точные Semgrep registry-пакеты проверяются в CI на каждом PR.
  Ручная проверка diff и дополнительный локальный Semgrep не заменяют эти проверки.
- Неподтверждённый текст согласия отсутствует, TOTP/восстановление credentials
  и ротация ключей остаются в дорожной карте. Только синтетические данные.
- Hash chain обнаруживает изменение истории, но не доказывает её подлинность
  против злоумышленника с полномочиями владельца БД или всего приложения;
  внешнее закрепление хэша и отдельный контур аудита — дальнейшее усиление.
