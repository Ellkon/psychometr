# AGENTS.md

Инструкции для AI-агентов (Claude Code, Codex, Cursor, Copilot, Gemini и других) и разработчиков, которые пишут код в этом репозитории. Это единый источник правил: `CLAUDE.md` и `GEMINI.md` только ссылаются на этот файл. Правила меняются здесь, а не в обёртках. Требования к продукту описаны в [`docs/TZ.md`](docs/TZ.md): это источник истины. Если задача противоречит ТЗ, остановись и спроси, а не выбирай вариант сам.

## Проект

«Клинический компас» — PWA для врача и пациента: шкалы PHQ-9/GAD-7, дневник доз, правила безопасности терапии, маршрутизация к психиатру, алерты. Работаем с медицинскими данными (152-ФЗ, 323-ФЗ). Ошибка в безопасности или в клиническом правиле стоит дороже, чем недоделанная фича.

## Структура

```
apps/api/          Fastify + TypeScript, REST + WebSocket
apps/web/          React 19 + Vite PWA
packages/shared/   zod-схемы и типы (общие для api и web)
content/           шкалы, препараты, правила, источники (JSON)
docs/              ТЗ, security-отчёты
infra/             docker compose, Caddy, скрипты бэкапа
```

## Команды

pnpm глобально не ставится: используй `npx pnpm@12.14.0 <команда>` (или алиас `alias pnpm='npx -y pnpm@12.14.0'`). Хранилище пакетов лежит в `.pnpm-store/` внутри репозитория. Для `docker compose` нужен `.env`, скопированный из `.env.example`, с заполненным `POSTGRES_PASSWORD`.

```bash
pnpm install
pnpm dev              # api + web
pnpm test             # vitest во всех пакетах
pnpm test:e2e         # playwright
pnpm lint
pnpm typecheck
pnpm db:generate      # drizzle-kit generate
pnpm db:migrate
docker compose up -d  # postgres, api, web/caddy (compose.yaml в корне)
docker compose -f compose.yaml -f compose.dev.yaml up -d postgres  # БД для pnpm dev
```

Перед тем как сообщить, что задача сделана, запусти `pnpm lint && pnpm typecheck && pnpm test`.

## Стек и соглашения

- TypeScript `strict`, без `any`. Если без него никак, нужен комментарий с причиной.
- Схемы запросов и ответов пиши на zod в `packages/shared`. Фронт и бэк импортируют их оттуда, не дублируют.
- Fastify: каждый роут с `schema` через `fastify-type-provider-zod`.
- БД только через Drizzle. Сырой SQL допустим в миграциях и с параметрами через `sql` template.
- Любое изменение схемы оформляется миграцией через drizzle-kit. Применённые миграции не редактируй.
- Frontend: TanStack Router и TanStack Query, UI на shadcn/ui и Tailwind, графики на Recharts.
- Интерфейс на русском языке. Код, идентификаторы и комментарии на английском.
- Новые зависимости добавляй только при реальной необходимости и пиши обоснование в PR. Проверяй лицензию (MIT, Apache-2.0, BSD, ISC).

## Безопасность: жёсткие правила

Нарушение любого пункта — блокер для merge.

1. **Доступ к пациенту.** Каждый роут, который читает или меняет данные пациента, вызывает `assertCanAccessPatient(user, patientId)` до любой работы с данными. Новый роут добавляется в IDOR-матрицу тестов.
2. **ПДн отдельно.** ФИО, телефон, дату рождения и СНИЛС читай и пиши только через модуль шифрования `patient_identity`. В остальных таблицах только UUID пациента.
3. **Логи.** В логи не попадают ПДн, клинические данные (ответы, баллы, препараты), пароли, токены приглашений и коды. Новые чувствительные поля добавляй в redact-список pino.
4. **Без сторонних ресурсов.** Никаких CDN, внешних шрифтов, аналитики, трекеров, Sentry SaaS и подобного. Все ассеты self-hosted.
5. **Секреты.** Не коммить `.env`, ключи и токены. Новая переменная окружения добавляется в `.env.example` с пустым значением.
6. **Аудит.** Вход, просмотр карты, изменения, подтверждения, отказы в доступе и операции с приглашениями пишутся в `audit_events`. Записи в этой таблице не обновляются и не удаляются.
7. **Приглашения.** Токены и коды генерируются только через `crypto.randomBytes` / `crypto.randomInt`. В БД хранятся только хэши: SHA-256 для токена, argon2id для кода. Открытое значение возвращается один раз.
8. **Пароли и коды** хэшируются argon2id. Своих криптографических схем не изобретай.
9. **Ввод.** Любой внешний ввод валидируется zod на границе.
10. **Заголовки.** Не ослабляй CSP, не добавляй `unsafe-inline` / `unsafe-eval` и не отключай helmet.
11. **Уведомления** вне приложения (SMS, push) не содержат медицинского текста.
12. **Клиентское хранилище.** В IndexedDB лежит только очередь неотправленных данных. При logout она очищается. Медицинские данные в `localStorage` не кладутся.

Если задача требует обойти одно из правил, остановись и спроси.

## Клиническая логика

- **Правила — данные.** Пороги, баллы, тексты пунктов шкал, противопоказания и критерии маршрутизации живут в `content/*.json`, а не в коде. В коде только движок, который их исполняет.
- У каждого правила есть `id`, `version`, `source` (ссылка на `content/sources.json`), `severity`, `message`, `suggested_action`. Правило без источника не принимается.
- Тексты шкал дословно совпадают с валидированной русской версией. Не переводи и не перефразируй сам. Если текста нет, оставь TODO и спроси.
- Отсутствующие клинические сведения обозначаются `unknown`, а не `false`.
- Система не назначает лечение. Любое предлагаемое действие оформляется как `Task` со статусом `requested`, который подтверждает врач.
- Пункт 9 PHQ-9 > 0 порождает critical-алерт врачу. Экстренная инструкция пациенту доступна офлайн.
- Каждый файл правил сопровождается эталонными сценариями в `__cases__/`. Изменил правило — обнови сценарии.
- LLM и генеративный ИИ в текущем объёме не используются.

## Тесты

- Vitest для логики api, движка правил (эталонные сценарии), RBAC и IDOR-матрицы «роль × эндпоинт × чужой пациент».
- Playwright для ключевых сценариев: приглашение и вход пациента, заполнение PHQ-9, алерт врачу с подтверждением, офлайн-отправка без дублей.
- Новый эндпоинт без теста на 403 для чужого пациента не принимается.
- Тесты не ходят во внешнюю сеть.

## Definition of Done

- [ ] Соответствует требованию из `docs/TZ.md` (номер FR/NFR указан в PR).
- [ ] `pnpm lint`, `pnpm typecheck`, `pnpm test` зелёные.
- [ ] Есть тесты, включая IDOR для новых роутов.
- [ ] Изменения схемы БД оформлены миграцией.
- [ ] Нужные действия пишутся в аудит.
- [ ] Новые чувствительные поля добавлены в redact.
- [ ] Если поменялись требования, обновлён `docs/TZ.md`.
- [ ] Проверки безопасности в CI (Semgrep, gitleaks, audit, Trivy, ZAP) зелёные.

## Git

- Одна ветка на задачу: `feat/<кратко>`, `fix/<кратко>`, `chore/<кратко>`.
- Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`, `security:`.
- Изменения попадают в `main` только через PR. Перед merge проводится security review диффа: встроенной командой твоего инструмента (например, `/security-review` в Claude Code) или вручную по разделу «Безопасность» этого файла.
- Агент не делает `push --force` в `main`, не переписывает историю `main` и не пушит без явной просьбы.

## Чего не делать

- Хардкодить пороги, тексты шкал и правила в коде.
- Генерировать рекомендации по лечению или off-label-подсказки.
- Подключать шкалы без подтверждённой лицензии (HADS, BDI-II, MMAS).
- Отправлять медицинские данные во внешние сервисы, включая Telegram.
- Добавлять видеосвязь, датчики, голосовую диагностику: они вне объёма.
- Отключать проверки CI, чтобы «прошло».
