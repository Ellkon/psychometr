# Клинический компас

PWA-ассистент врача для сопровождения терапии тревожных и депрессивных расстройств.
Решение по диагностике и лечению принимает врач — приложение не назначает терапию.

**Статус:** реализованы каркас и этап 2 (вход, права, приглашения, аудит,
шифрование персональных данных). Шкалы и клинические правила — следующие этапы.
**Пока используйте только синтетические данные.** Это не готовый к клинической
эксплуатации или юридически аттестованный продукт.

- [`docs/TZ.md`](docs/TZ.md) — требования и план.
- [`AGENTS.md`](AGENTS.md) — правила разработки.
- [`SECURITY.md`](SECURITY.md) — модель угроз.
- [`docs/development/stage-2.md`](docs/development/stage-2.md) — устройство этапа 2,
  зависимости, команды и ограничения.
- [`docs/security/stage-2-review.md`](docs/security/stage-2-review.md) — результаты
  проверки, включая то, что пока не проверено.

## Быстрый старт: изолированный локальный стенд

Нужны Node 22, pnpm 10.34.7 и Docker Compose v2.

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm setup:local

docker compose --env-file .env -f infra/docker-compose.yml up -d --build
pnpm admin:bootstrap
```

`setup:local` создаёт `.env` со случайными независимыми ключами и паролями
(права файла 0600), **не перезаписывает существующий файл и не печатает секреты**.
Не коммитьте и не пересылайте `.env`. Сохраните ключ шифрования безопасно:
без него нельзя прочитать ранее зашифрованные данные.

Откройте **https://localhost:8443**. В локальном стенде сертификат подписан
внутренним центром Caddy; браузер предупредит об отсутствии доверия. Исключение
допустимо только для этого локального синтетического стенда. Для развёртывания
нужны корректный домен и доверенный TLS-сертификат.

Первоначальные `ADMIN_EMAIL` / `ADMIN_PASSWORD` находятся в вашем локальном
`.env`. После первого создания администратора уберите эти bootstrap-значения
из файла и храните пароль в менеджере паролей. Повторное создание первого
администратора командой блокируется. В интерфейсе администратор создаёт врача;
врач создаёт пациента и приглашение.

### Перед активацией пациента

Утверждённого текста согласия в репозитории **нет**, юридический текст не
генерировался. Положите согласованный документ в `infra/consent/approved.txt`
(UTF-8), задайте в `.env`:

```dotenv
CONSENT_TEXT_PATH=/run/consent/approved.txt
CONSENT_VERSION=your-approved-version
```

Затем пересоздайте API: `docker compose --env-file .env -f infra/docker-compose.yml up -d api`.
При изменении текста нужна новая версия; прежние версии необходимо сохранять
в вашем архиве согласований. Пока документ не подключён, вход по приглашению
возвращает 503, а интерфейс объясняет причину. Синтетический текст создаётся
только тестами и **не является согласием настоящего пациента**.

### Если сохранился volume от этапа 1

Init-скрипт PostgreSQL выполняется только при создании пустого volume. Старый
volume сам не получит новые роли/права/пароли. Если это **ненужные синтетические
данные**, остановите стенд и удалите volume явно (это уничтожает данные):
`docker compose --env-file .env -f infra/docker-compose.yml down -v`.
Затем запустите стенд заново. Не выполняйте это для ценной или реальной БД:
для неё нужен отдельный план миграции и проверенный бэкап.

## Команды разработчика

```bash
pnpm dev              # API + Vite; нужны .env и доступная локальная PostgreSQL
pnpm build
pnpm lint
pnpm typecheck
pnpm test             # 80 проверок, в том числе на настоящем PostgreSQL 16
pnpm format:check
pnpm check:content
pnpm audit --audit-level=high
pnpm db:generate      # создаёт новую миграцию из Drizzle-схемы
pnpm db:migrate       # только MIGRATION_DATABASE_URL, отдельная роль migrator
pnpm admin:create     # bootstrap без Docker; DATABASE_URL должен быть доступен локально
pnpm test:e2e         # запущенный HTTPS-стенд + браузер Playwright + тестовый администратор
```

В `.env`, созданном для Compose, адрес БД — `db` (внутри контейнеров).
Для `pnpm dev` с БД вне Docker задайте свой `DATABASE_URL`/`MIGRATION_DATABASE_URL`.
В браузере нужен HTTPS-origin, совпадающий с `PUBLIC_ORIGIN`; API вызывается
только относительными `/api/...` через прокси. За одним доверенным прокси
используйте `TRUST_PROXY=one-hop`, при прямом обращении к API — `none`.

`pnpm test` самостоятельно поднимает одноразовый PostgreSQL 16 через Unix-сокет,
применяет миграции и проверяет права роли `app`. Docker и внешняя сеть для самих
тестов не нужны; бинарники скачиваются вместе с dev-зависимостями при установке.
Запускайте тесты обычным пользователем, не root. Linux/macOS поддерживаются
тестовым harness; для Windows используйте WSL2 или CI.

Playwright-отчёты и trace могут содержать тестовые данные: браузерные сценарии
запускаются **только на изолированных синтетических стендах**, не на клинической БД.

## Структура

```text
apps/api/          Fastify, auth, RBAC, Drizzle, AES-GCM, аудит
apps/web/          React PWA, формы входа, пациенты, приглашения, аудит
packages/shared/   общие zod-контракты
content/           заготовки клинического контента, без выдуманных текстов шкал
infra/             Compose, Caddy, роли БД, внешний текст согласия
e2e/               браузерные сценарии
```
